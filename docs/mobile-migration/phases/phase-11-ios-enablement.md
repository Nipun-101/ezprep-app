# Phase 11 — iOS Enablement

## Objective
Ship the same app on iOS: an iOS build via EAS, iOS-specific configuration (bundle ID, Google iOS client, Keychain, permissions strings), platform UX adjustments (swipe-back rules, safe areas, keyboard), App Store compliance (including the Sign in with Apple question), and TestFlight → App Store release.

## Prerequisites
Phase 10 done (Android in production). An Apple Developer Program account. Decision **U-33** (Sign in with Apple). The iOS bundle ID (U-29). A physical iPhone for testing.

## Source documents
`../mobile-authentication.md`, `../package-strategy.md`, `../accessibility-analysis.md`, `../risk-register.md` (R-19), `../engineering-rules.md`.

## Web reference (read-only)
None needed beyond the earlier phases.

## Target mobile changes
- `app.config.ts` `ios`: `bundleIdentifier`, `supportsTablet` decision, `infoPlist` usage strings only for the features used, `ITSAppUsesNonExemptEncryption` declaration (standard HTTPS only → typically false; verify), the Google sign-in iOS URL scheme (reversed client id) via the config plugin.
- Google Cloud: an iOS OAuth client; the backend must accept its audience if the ID-token flow uses it (extension of U-02).
- MSG91 SDK iOS support (verify; fallback to backend OTP).
- Platform files (`*.ios.tsx`) only where behavior differs: the runner swipe-back gesture disabled (already `gestureEnabled: false`), share sheet differences, the date picker presentation.
- Optional: Sign in with Apple (`expo-apple-authentication`) **only if U-33 requires it**, which needs a backend endpoint (a new backend contract).

## Files to create
iOS-specific assets (icon set generated by Expo from the source icon), `store/ios/` listing materials, any `*.ios.tsx` files required.

## Files that may be modified
`app.config.ts`, `eas.json` (iOS profiles + submit config), the auth adapters (iOS config), `../MOBILE_STATUS.md`.

## Do-not-touch boundaries
Android behavior must not change (regression run on Android required). No feature changes.

## Dependencies
`expo-apple-authentication` (conditional on U-33). Everything else already supports iOS (verify the MSG91 SDK).

## Implementation tasks
1. Create the iOS app in App Store Connect; configure EAS credentials (distribution certificate, provisioning profile).
2. Build the development client for iOS; run on the physical iPhone.
3. Verify every phase's device checklist on iOS (VoiceOver instead of TalkBack, Dynamic Type instead of the font scale).
4. Google sign-in iOS client + URL scheme; OTP SDK on iOS (or the backend fallback).
5. Resolve U-33. Implement Apple sign-in only if required and backend-supported.
6. App Privacy ("nutrition label") answers aligned with Play Data Safety; account deletion is required by App Store rules as well (already built in phase 10).
7. TestFlight internal → external testing → App Store review → release.

## Requirements
- **UX:** iOS conventions where they differ (the back swipe on non-runner screens, the share sheet, the date picker); the same visual design.
- **API:** No change unless Apple sign-in is required.
- **Security:** Keychain via SecureStore (`AFTER_FIRST_UNLOCK`); no ATS exceptions.
- **Performance:** The same budgets on a mid-range iPhone.
- **Testing:** The Maestro suite runs on the iOS simulator; a manual run on the physical iPhone.

## Acceptance criteria
The iOS app passes App Store review and runs all journeys with parity to Android; the Android regression run passes.

## Manual device checklist
- [ ] All phase checklists on the iPhone (VoiceOver, Dynamic Type, airplane mode).
- [ ] Google and OTP sign-in on iOS.
- [ ] Runner: swipe-back disabled, the leave dialog via the header back, backgrounding behavior.
- [ ] Share image, legal links, account deletion.

## Risks
R-19, R-01 (the iOS client audience), R-02 (the MSG91 iOS SDK).

## Rollback / isolation
iOS release is independent of Android. TestFlight gates production. Platform-specific code is confined to `*.ios.tsx`/config.

## Completion checklist
- [ ] U-33 decision recorded.
- [ ] App Privacy submitted.
- [ ] `MOBILE_STATUS.md` updated.

## Definition of done
EZ Prep is live on the App Store with parity to Android, and the Android build is unaffected.
